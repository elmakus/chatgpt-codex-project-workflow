### Must preserve

- M01 branch/workstream resolution and manifest ↔ Task Board binding remain authoritative before branch-isolated mutable execution state is interpreted.
- Exactly one Card may be `in_progress` per selected Task Board; unrelated workstreams do not block each other merely because another board has active work.
- Existing default `implementation/TASK_BOARD.yaml` projects remain legal and are not migrated or mutated merely because intake discovers them.
- `#issue` and `#feature` are explicit entry directives only; ordinary prompts retain normal router behavior and a completed intake returns to the router rather than becoming a session-scope boundary.
- `#feature` may start discovery but never counts as Brainstorming → Project Definition promotion authorization.
- New workstream identity is durable, branch-isolated and collision-safe; stacked parent selection is based on a real parent-only dependency, never convenience.
- Intake must not read or mutate an unrelated workstream Task Board as the current state merely because that workstream exists or exposed a symptom.
- Same-workstream rediscovery recovers the existing durable workstream instead of creating a parallel lane.
- Behavioral review/integration requirements remain intact; M02 may classify the path but must not weaken the later M03/M04 review/integration gates.
- No mixed/Codex/legacy parallel-lane or executor-routing semantics enter `chatgpt_only`.

### Must not / rationale that must travel

- Do not make explicit intake wait behind an unrelated default/workstream `in_progress` Card or pending review before intake can establish/select its own state context.
- Do not treat mere file overlap as a parent/dependency decision.
- Do not duplicate Card/milestone execution state into the workstream manifest; intake lifecycle/location metadata may live there because it is routing/workstream-lifecycle state.
- Do not fully implement the micro-fix execution/review contract, worktree policy or integration-refresh mechanics owned by M03/M04.
- Do not add user-facing fresh-handoff template expansion owned by M05.

## Dependencies

## Outcome

An explicit operator `#issue` or `#feature` directive enters a deterministic ChatGPT-only intake layer before ordinary phase/execution selection, creates or recovers one exact branch-isolated workstream, chooses the correct independent/stacked base and smallest legal downstream path, and then returns to normal router-owned continuation.

## Scope

### Included

- add `workflow/chatgpt_only/INTAKE.md` as the canonical issue/feature intake contract;
- update `workflow/chatgpt_only/ROUTER.md` so an explicit current operator marker takes precedence over unrelated mutable execution state, while active durable intake recovery also routes back to Intake;
- update `workflow/chatgpt_only/WORKSTREAMS.md` with intake-owned identity/naming/recovery rules and the boundary between manifest routing metadata and Task Board execution state;
- extend `workflow/chatgpt_only/WORKSTREAM_TEMPLATE.yaml` only as needed for durable intake routing/recovery metadata;
- define issue intake discovery/diagnosis, base selection, independent-vs-stacked classification, branch/workstream creation and micro-fix-vs-normal-path classification;
- define feature intake workstream creation and handoff into Brainstorming/Research while preserving explicit Definition promotion authority;
- define stable workstream-ID / branch naming and collision handling;
- define idempotent recovery when an intake branch/workstream already exists.

### Excluded

- detailed micro-fix execution/review lifecycle (M03);
- full branch-local execution/review/recovery adaptation beyond intake routing (M03);
- local worktree/equivalent checkout rules and integration refresh/rebase/retarget mechanics (M04);
- final user-facing handoff templates, migration UX and full E2E regression closure (M05);
- changes to mixed, Codex or legacy policy namespaces.

## Acceptance

- an explicit `#issue` reaches Intake before an unrelated active/default Task Board can block normal execution selection;
- issue intake establishes/reproduces the problem when practical, discovers relevant branches/PRs/workstreams, chooses default integration target unless parent-only state is genuinely required, and creates/reuses a distinct durable fix workstream before implementation mutation;
- issue intake classifies the smallest legal path as micro-fix or normal workflow without pretending M03 mechanics already exist;
- an explicit `#feature` creates/reuses one feature workstream and enters discovery without recording or implying Definition promotion authorization;
- ordinary prompts with no operator directive continue through the existing router path;
- active intake state is recoverable from exact branch + manifest/intake record without previous chat narrative;
- duplicate/same-workstream discovery recovers the existing workstream rather than creating a second lane;
- identity/branch naming is stable and collision-safe, and stacked metadata records a real parent dependency;
- intake does not modify unrelated active workstream state;
- no foreign-policy execution/orchestration semantics are introduced.
