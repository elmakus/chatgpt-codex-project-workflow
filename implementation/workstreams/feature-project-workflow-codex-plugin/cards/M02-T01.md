### Must preserve

- Package the plugin in this repository; do not create or depend on a second repository.
- Plugin name is `pw`; exactly one bundled normal Skill exists and is named `project-workflow`, exposed by current Codex namespacing as `$pw:project-workflow`.
- The repository root is the plugin root so installed plugin content carries the canonical sibling `workflow/` tree; marketplace metadata must resolve the local plugin source to that root.
- `workflow/CONTEXT_ROUTING.md`, the selected policy tree and project `PROJECT.md` remain canonical. The Skill and startup bootstrap may contain only bounded entry/routing instructions, not copied workflow policy.
- Activation must use the M01-selected minimal SessionStart mechanism and current hook trust semantics; testing may bypass hook trust only inside disposable isolated runtime state.
- Bootstrap must honor the workspace's `PROJECT.md` and canonical policy routing; it must not hard-code consumers to `codex_only` or `chatgpt_only`.
- Keep the generic Git-backed Codex marketplace/update mechanism. Add no plugin-local updater, timer or release poller.
- Ordinary canonical workflow-module edits must propagate through the packaged repository without requiring a Skill edit when bootstrap semantics are unchanged.
- Full fresh/resume/compaction lifecycle acceptance and the `#issue/#feature` versus explicit-Skill intake UX decision remain M03-owned.

### Must not / rationale that must travel

- Do not add duplicate issue/feature Skills or duplicate policy prose to `SKILL.md`; both would create synchronization/UX drift explicitly rejected by Definition R3.
- Do not mutate the user's live Codex marketplace, plugin installation or config state for verification. Use disposable isolated state for runtime tests.

## Acceptance

1. The repository exposes a valid Git-backed marketplace whose `pw` source resolves to the repository/plugin root.
2. The root plugin manifest identifies `pw` and exposes the default Skill directory without duplicating workflow policy or declaring unsupported manifest fields.
3. Exactly one bundled normal Skill exists: `project-workflow`; its explicit native identity is compatible with `$pw:project-workflow`.
4. The Skill is a thin bootstrap that directs Codex through workspace `PROJECT.md` and canonical `workflow/CONTEXT_ROUTING.md`, without embedding policy-module semantics.
5. The SessionStart bootstrap is bounded, uses installed `PLUGIN_ROOT` canonical paths, emits valid SessionStart `additionalContext`, and does not hard-code an execution policy.
6. Deterministic tests prove a canonical `workflow/codex_only/*` content change would be carried by the package/update path without requiring any Skill-content change.
7. No plugin-local updater/timer/poller exists.
8. An isolated current-runtime smoke, when runnable, installs/enables from the accepted marketplace source, discovers `pw:project-workflow`, and verifies the bootstrap against the production package. If the current runtime is concretely unavailable, preserve exact static/contract evidence and route the runtime gap under normal workflow blocker rules rather than weakening acceptance.
