### Must preserve

- A merged workstream source branch may disappear immediately after merge without making closure/recovery fail.
- Before final merge, every unique recovery artifact is either included in the exact merge subject or already durable on the integration target / immutable GitHub PR or merge state.
- Post-merge reconciliation must operate from target-side durable state + immutable Git/PR evidence; it must not recreate or require the deleted source ref.
- GitHub automatic merged-head deletion is preferred operationally when available, but workflow correctness must not depend on that repository setting.
- A surviving merged branch or terminal unmerged branch may become `safe_to_delete` only after exact terminal safety, no live obligation, and exact ref/head evidence.
- Fallback cleanup state is workstream-local durable state, not a mutable repository-global registry.
- `delete/*` alias creation or any second-ref same-SHA rename emulation is forbidden.
- Branch/head movement invalidates stale cleanup readiness until revalidated.
- Original manifest `branch` and Task Board `execution_ref.branch` remain provenance after deletion and must not be rewritten to the target.
- Stacked child dependency satisfaction is proven from target/Git evidence after parent integration; deleted parent source refs are never required.
- Legacy/default mode and already-completed historical workstreams remain valid without migration churn.
- Repository-setting mutation (`delete_branch_on_merge`) and physical fallback deletion are separate external writes; this Card does not perform either.
- Codex-only policy is out of scope.

### Must not / rationale that must travel

- Do not solve the transitional post-merge state by weakening manifest ↔ Task Board identity checks or by falling back to root `implementation/TASK_BOARD.yaml`.
- Do not treat closed PR state alone as cleanup authority.
- Do not make the cleanup marker durable only on the branch that it authorizes deleting; terminal unmerged cleanup must retain recovery/cleanup truth independently of that ref before `safe_to_delete`.
- Do not force-update/rename refs to manufacture cleanup success.

ChatGPT-only workstream finalization, terminal recovery and branch cleanup remain correct whether GitHub deletes a merged PR head immediately, leaves it present, or a workstream terminates unmerged and later becomes eligible for cleanup.

## Acceptance

1. A final merge may be followed by immediate source-branch disappearance; same-session or fresh-session closure can still resolve the exact workstream from the target-side package and immutable PR/merge evidence before final terminal metadata is reconciled.
2. Pre-merge rules require every unique recovery artifact to be in the merge subject or otherwise already durable independently of the source branch.
3. Post-merge close/readback and closure-only reconciliation never require recreating or reading the deleted source branch.
4. The manifest cleanup fallback records exact original ref + verified head + evidence and only exposes `safe_to_delete` after terminal safety; head movement makes readiness stale.
5. A terminal unmerged workstream cannot be marked `safe_to_delete` until its required closure/recovery/cleanup truth is durably preserved independently of the source branch and no live workstream obligation remains.
6. A merged branch that survives auto-delete remains a successful integration and uses the same exact fallback only after terminal safety.
7. No active ChatGPT-only policy/template recommends or creates `delete/*` alias refs as rename emulation.
8. Stacked child recovery/integration works after a merged parent source branch disappears by proving parent dependency satisfaction on the integration target and running normal refresh/reconciliation.
9. Legacy/default and completed historical workstreams remain valid without repository-wide migration.
10. GitHub auto-delete configuration and physical fallback deletion remain separate external writes and are not implementation correctness prerequisites.
11. Codex-only behavior is unchanged.
12. The resulting contract is idempotent: repeated target-side closure/readback after branch disappearance does not duplicate state or weaken exact identity/evidence checks.
