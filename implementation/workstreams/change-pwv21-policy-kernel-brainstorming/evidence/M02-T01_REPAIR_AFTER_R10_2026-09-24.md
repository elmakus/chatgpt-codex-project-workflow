### R10-F01 root correction

The Result reconciliation seam now has one semantic acceptance gate before both fresh and stale-success actions.

It requires:
- `status = success`;
- no blocker on a successful Result;
- required test/evidence outcomes to be present;
- every reported test to be GREEN;
- no failed readback.

Therefore freshness equality or a stale-result safety proof can no longer convert a failed, blocked, RED/not-run-test, missing-required-evidence, or failed-readback Result into `accept` / `reuse` / `rebase` / `reconcile`.

Generalized regression coverage exercises the sibling fresh/stale cases, including the no-mutation-postcondition failed-readback case.

### R10-F02 root correction

Execution Obligation freshness now includes a deterministic fingerprint of the mechanically determining registered-rule metadata: rule ID, precedence, predicate, declared inputs and outcome. The Obligation ID therefore changes when the applicable mechanical rule materially changes even if current input values and owner role remain unchanged.

The production kernel derives this fingerprint itself, refreshes it during reconciliation, and rejects caller substitution. A material rule drift makes an old Result stale.

The execution-obligation compile seam also rejects matching `stop` and `recovery` decisions; only registered matching `route` rules may be compiled as Execution Obligations.

Regression coverage includes material rule-outcome drift, stale reconciliation after rule drift, caller fingerprint substitution, and both stop/recovery sibling cases.
