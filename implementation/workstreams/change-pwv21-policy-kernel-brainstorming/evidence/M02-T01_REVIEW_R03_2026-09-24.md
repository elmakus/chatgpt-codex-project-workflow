The current M02 suite never validates payloads against the checked-in JSON Schemas. `test_schemas_are_closed_and_exclude_runtime_telemetry_fields` only inspects selected schema structure/property names; version and payload failures are exercised through the Python validator instead.

More importantly, the checked-in JSON Schema and executable validator accept different payload languages:

1. `$defs.exact_ref.path` in both schemas is only a non-empty string. The executable `validate_exact_ref()` applies `_safe_path()`, rejecting absolute paths and parent (`..`) path segments. Therefore a payload such as an absolute exact-ref path can be schema-valid while executable validation rejects it.
2. `freshness.material.inputs` in the Obligation schema excludes telemetry names only with a top-level `propertyNames` rule. The executable `_reject_telemetry_keys()` recursively rejects telemetry keys in nested mappings/lists. A nested `{"nested":{"provider":"x"}}` therefore passes the schema surface but fails executable validation.
3. Mutation condition `equals` is unconstrained in the schema, while the executable recursively rejects telemetry keys inside it. This is another concrete schema/validator divergence.
4. The Result schema has the same exact-ref path mismatch.

That means the versioned canonical JSON Schemas do not currently express the same accepted contract as the executable validator, and the required schema-validation matrix is absent. This is a material acceptance failure for `PWV21-REQ-018` and the P2 M02 acceptance/verification contract; GREEN cannot be issued merely because the executable validator and existing CI are GREEN.
