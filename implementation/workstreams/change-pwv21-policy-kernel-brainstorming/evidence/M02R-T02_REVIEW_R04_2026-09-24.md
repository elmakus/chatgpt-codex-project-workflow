### F1 — epoch reset still accepts a fabricated immutable subject at an accepted path

Load-bearing surface: PWV21-REQ-111 and Card acceptance requiring reset only for a **material accepted authority/acceptance redesign** plus durable reset basis.

`tools/state_contract.py::validate_review` now correctly requires the reset subject repository to match the reviewed project and `validate_review_history` restricts the reset path to the exact acceptance path or a Card-accepted authority path. However, neither layer proves that the claimed `commit/path/blob` actually exists or equals the accepted redesign content.

The focused state test demonstrates the remaining bypass: `test_review_epoch_reset_requires_material_accepted_redesign_basis` constructs `epoch_reset_subject` with arbitrary synthetic 40-hex commit/blob values, changes only its path to the exact Task Card acceptance path, and expects `validate_review_history([base, reset])` to succeed. Therefore an E01→E02 reset can still be manufactured without any readback proving a material accepted redesign.

Required correction: bind the reset subject to exact repository content that is durably accepted for the Card — at minimum validate the claimed commit/path/blob against repository readback (or an equivalent exact accepted-content binding), not merely repository/path membership and 40-hex shape. Add a negative fixture proving a fabricated/nonexistent or blob-mismatched exact acceptance/authority subject cannot reset the epoch, while a real accepted redesign can.

### F2 — a multi-class RED closure overcounts failed rounds for classes that did not fail

Load-bearing surface: PWV21-REQ-113/PWV21-REQ-137 and Card acceptance requiring a default ceiling of **3 failed repair→closure-verification rounds per material defect class**.

`tools/review_contract.py::review_convergence_state` handles every RED `closure_verification` by iterating all `material_defect_class_ids` on the attempt and incrementing each class after a qualifying subject transition. But the durable closure contract has one aggregate attempt verdict and allows a closure attempt to cover multiple findings/classes. `material_defect_class_ids` cannot mean “failed classes only”, because GREEN closure attempts are also required to carry non-empty class IDs.

Concrete counterexample:
1. Source RED discovery freezes F1/class-a and F2/class-b.
2. A repair changes the subject and one closure attempt verifies both classes.
3. class-a is fixed, class-b remains blocking, so the aggregate closure verdict is RED.
4. Current accounting increments the failed-round counter for **both** class-a and class-b.
5. Repeating this pattern can force class-a to its three-round convergence breaker even though class-a did not fail three repair→closure rounds.

The focused tests exercise only single-class RED closure accounting and do not falsify this case.

Required correction: durably identify which defect class(es) actually failed each RED closure round, or otherwise constrain/normalize closure attempts so per-class failure accounting is unambiguous. Add a multi-class negative fixture proving a RED caused by one class does not consume a failed round for another successfully verified class.
