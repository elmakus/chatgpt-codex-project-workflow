## Blocking findings

### 1. Result subject is not actually bound during reconciliation

`validate_execution_result()` only validates that `result.subject` is syntactically an exact ref. `reconcile_execution_result()` verifies `obligation_id` and the original freshness fingerprint, but never requires `result["subject"] == obligation["subject"]`.

Therefore a result can carry the correct obligation/fingerprint while naming a different exact subject and still reconcile to `accept` when current freshness is unchanged. This violates PWV21-REQ-019 / PWV21-REQ-026 / PWV21-REQ-028 and the Card requirement for exact result identity/freshness binding.

### 2. Material obligation fields can drift outside the fingerprint/identity checks

The obligation duplicates `prerequisites`, `constraints`, `completion` and `mutation` both at top level and inside `freshness.material`. Validation checks subject and authority equality across those surfaces, but does not require equality for the other duplicated fields. A transported obligation can therefore alter top-level completion or mutation conditions while retaining the old freshness fingerprint and `obligation_id`, and executable validation accepts it.

Additionally, `role` is an exact required obligation field but is not bound by either freshness material or the current `obligation_id` derivation, so it can be changed without changing identity.

This breaks the deterministic binding/freshness and governed-mutation guarantees required by PWV21-REQ-019, PWV21-REQ-024, PWV21-REQ-025 and PWV21-REQ-031.

## Additional contract drift found during the same review

- Executable exact-ref validation accepts repository strings with more than one slash (for example `owner/repo/extra`) while both JSON schemas require exactly `owner/name`; executable validation can therefore accept a payload that the declared schema rejects.
- `workflow/EXECUTION_CONTRACTS.md` documents only `reuse` for a positively proven stale result, while the accepted authority and implementation expose `reuse`, `rebase` and `reconcile`.

## Required bounded correction

Within M02 only:

1. enforce exact result-subject equality with the obligation subject before any `accept/reuse/rebase/reconcile` result;
2. enforce top-level ↔ freshness-material equality for every duplicated determining field;
3. bind `role` into deterministic obligation identity (or equivalently into mandatory freshness material) so role drift invalidates the envelope;
4. align executable exact-ref repository validation with the schema;
5. add negative regression tests for all of the above and align the human-readable stale-action contract with the implemented/accepted action set.
