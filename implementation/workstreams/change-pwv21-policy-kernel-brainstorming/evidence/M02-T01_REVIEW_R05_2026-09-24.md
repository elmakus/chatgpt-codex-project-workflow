## RED finding

### Executable schema-version validation accepts JSON boolean `true` as version 1

Both `validate_execution_obligation()` and `validate_execution_result()` enforce the supported version with Python equality:

`payload["schema_version"] == SUPPORTED_SCHEMA_VERSION`

with `SUPPORTED_SCHEMA_VERSION = 1`.

In Python, `True == 1` is true. Consequently an otherwise valid JSON payload containing `"schema_version": true` passes the executable validator. The Draft 2020-12 schemas use `"const": 1` and correctly reject JSON boolean `true`, so the executable contract is weaker than the declared schema and the two validation surfaces disagree.

The existing version tests cover unsupported numeric version `2` but do not cover boolean type confusion. This violates the M02 requirement for versioned typed contracts and fail-closed unsupported/breaking version handling (PWV21-REQ-018 and PWV21-REQ-030), and it breaks schema/runtime parity expected by the Card acceptance surface.

Required bounded correction:
- make executable schema-version validation reject booleans while preserving the intended JSON numeric version semantics;
- add executable regression coverage for boolean `schema_version` on both Obligation and Result;
- add the same cases to the real Draft 2020-12 invalid matrix so schema/runtime behavior remains locked together.
