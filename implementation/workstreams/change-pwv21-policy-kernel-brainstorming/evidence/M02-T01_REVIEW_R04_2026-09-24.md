## RED findings

### 1. Canonical JSON serialization permits non-JSON numeric values

`tools/obligation_contract.py::canonical_json()` calls Python `json.dumps` without `allow_nan=False`. Python therefore serializes non-finite floats as bare `NaN`, `Infinity`, or `-Infinity`. Those tokens are not valid interoperable JSON, yet arbitrary determining inputs and mutation-condition values are part of the transport-neutral typed Obligation surface.

This means a caller can compile an obligation whose supposedly canonical JSON serialization is not valid JSON. The current tests do not exercise non-finite values.

Required bounded correction: make canonical serialization reject non-finite/non-serializable JSON values with the typed contract error and add negative regression coverage.

### 2. Draft 2020-12 schema remains weaker than executable Obligation validation

The real JSON Schema gate is now executed, but the checked schema still accepts payloads that `validate_execution_obligation()` rejects:

- `$defs.telemetry_free_json` forbids only exact lowercase property names, while executable validation lowercases every key before comparing against the forbidden telemetry vocabulary. For example nested `Model` is schema-valid but executable-invalid.
- `freshness_material.prerequisites` and `freshness_material.constraints` require only `minLength: 1`, while executable validation requires non-whitespace strings. The duplicated top-level arrays have `pattern: "\\S"`, but the freshness copies do not.

The existing Draft 2020-12 invalid matrix covers lowercase nested telemetry and a blank top-level role, so these remaining parity gaps are not detected.

Required bounded correction: align the schema with the executable contract and extend the real-schema negative matrix to cover case-variant telemetry and whitespace-only freshness entries.
