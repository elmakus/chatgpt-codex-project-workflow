## Verdict

RED.

The complete material finding set from this pass contains two independent defect classes.

### R10-F01 — semantic Result acceptance is not gated before freshness acceptance

`tools/obligation_contract.py::reconcile_execution_result()` validates the Result shape and exact obligation/freshness/subject bindings, then may return `accept`, `reuse`, `rebase`, or `reconcile` without first requiring the Result itself to be semantically successful.

Consequences across sibling cases:

- a structurally valid Result with `status = "failed"` can reach `accept` when freshness is unchanged;
- a structurally valid Result with `status = "blocked"` can reach `accept` when freshness is unchanged;
- the same non-success Result can reach stale `reuse`/`rebase`/`reconcile` when a safety proof object is supplied;
- a nominally successful Result can carry RED / not-run test outcomes and still reach the freshness acceptance path;
- a failed readback is rejected only when mutation postconditions happen to be non-empty; with no postconditions the freshness path does not treat failed readback as an acceptance blocker.

This makes freshness/binding validation sufficient for an acceptance-like return even though PWV21-REQ-026 requires semantic result status/tests/evidence/readback data and PWV21-REQ-028 requires revalidation before accepting a Result rather than blind acceptance. The P2 M02 acceptance surface requires stale results to be reconciled/re-routed and blind acceptance to be impossible.

Required correction class: introduce one semantic acceptance gate shared by fresh and stale-success paths; non-success status and materially failed test/readback outcomes must not produce acceptance/reuse actions. Cover failed, blocked, RED/not-run test, failed-readback, and stale sibling cases.

### R10-F02 — Obligation identity/freshness is not bound to the registered rule content that determined the obligation

`PolicyKernel.compile_obligations()` verifies that a registered rule matches and derives the owner role plus declared input values. However the emitted Obligation/freshness identity binds only `rule_id`, role, subject, freshness material and the selected input values. It does not bind the registered rule's mechanically determining metadata such as disposition/outcome obligation, predicate/input declaration, or precedence.

A material registry-rule change can therefore leave the emitted Obligation byte-identical when the rule ID, owner module and selected current input values remain the same. For example, changing the registered K011 outcome obligation while retaining its owner and input values changes the applicable rule but does not participate in the current obligation fingerprint/ID.

The production compile seam also accepts any matching registered decision without checking that its disposition is executable `route`; a matching `stop` rule can therefore be packaged as an Execution Obligation if the seam is called directly.

This violates the PWV21-REQ-024 requirement that `obligation_id` be content-derived from the applicable rule, subject and relevant fingerprint, and the ADR-PWV21-002 requirement that obligation identity/freshness be bound to only the canonical inputs that materially determined the obligation. It also weakens preservation of existing stop semantics.

Required correction class: bind an exact deterministic fingerprint of the mechanically determining registered-rule metadata into Obligation freshness/identity, revalidate that binding in the production kernel, and reject non-route decisions at the Execution Obligation compile seam. Add generalized regressions for material rule drift and stop/recovery rules.
