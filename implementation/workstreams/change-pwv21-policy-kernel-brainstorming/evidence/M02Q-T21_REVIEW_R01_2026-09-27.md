## M02Q-T21-F01 — exact `close_completion` can stop before required Close evidence is complete

Severity surface: correctness.

The new production path treats an exact workstream-local `close_completion` record plus an exact terminal Board as sufficient durable completion proof. `verify_durable_close_completion_from_state()` validates the completion locator/record, all Cards DONE and RF014 JIT terminality, then returns `approved_scope_durably_complete`. It does **not** prove the GREEN Final Integration Review required by PWV21-REQ-105, the required target-side recovery-package state from RF011, or the authoritative final-observation / cleanup reconciliation already implemented by `verify_final_observation_reconciliation_from_board()`.

The positive H027 router fixture demonstrates the bypass rather than preventing it: it creates an all-DONE sample Board, writes a minimal version-1 completion record containing only `workstream_id`, `state = "complete"` and exact `terminal_board`, and expects `stop/end_of_scope_stop`. No final integration review, recovery-package completion or cleanup-reconciliation proof is installed in that fixture.

This conflicts directly with the T21 acceptance rule that incomplete recovery or cleanup readiness cannot stop, and with REQ-105 that Workstream close requires GREEN Final Integration Review plus all required acceptance evidence. Exact Git identity proves bytes and ancestry; it does not by itself prove that those prerequisite Close obligations were satisfied.

Load-bearing evidence:
- `tools/close_contract.py` at product SHA `d1d3495...`: `verify_durable_close_completion_from_state` validates only the completion record, terminal Board, all-DONE and terminal JIT before returning approved completion.
- `tools/router.py`: the K012 all-DONE branch runs `done_close_gate`, `jit_terminality_gate`, then `durable_close_completion_stop`; it does not call the existing RF011/final-observation/cleanup gates before stopping.
- `tests/test_router.py::test_h027_close_reentry_requires_durable_completion_before_stop`: the minimal completion fixture reaches end-of-scope stop without those required Close proofs.

Required correction: durable completion must be derived from or bind exact proof of all still-required Close acceptance prerequisites rather than accepting a self-attested `state = "complete"` record as sufficient terminal truth.

## M02Q-T21-F02 — production composition fabricates continuation-oracle inputs and can bypass an explicit authorization stop

Severity surface: correctness.

`durable_close_completion_stop()` calls `close_continuation()` with:
- `approved_scope_durably_complete=True`,
- `next_authorized_obligation=False`,
- `explicit_authorization_gate_due=False`.

The last two values are hard-coded rather than derived from durable Close state. The oracle itself correctly gives an explicit authorization gate precedence over end-of-scope stop and rejects terminal completion when another authorized obligation remains, but the production integration makes those branches unreachable once an accepted `close_completion` is present.

The implementation evidence cites existing `close_continuation` unit controls for authorization/live-write behavior, but those controls do not exercise the production selector composition. T21 acceptance explicitly requires authorization-stop versus live-write-continue preservation, and REQ-107 requires deterministic continuation after input until the next real stop. A terminal selector must not manufacture `False` for these durable-state questions.

Load-bearing evidence:
- `tools/close_contract.py::close_continuation` correctly returns `authorization_stop` when `explicit_authorization_gate_due` is true and errors on terminal completion with a remaining authorized obligation.
- `tools/router.py::durable_close_completion_stop` hard-codes both values false before emitting `end_of_scope_stop`.
- The H027 router tests contain no selector-level authorization-due fixture with an installed completion record.

Required correction: derive the oracle inputs from exact durable Close authority/state, or make the verified completion proof itself cryptographically/exactly bind the absence/completion of those obligations so the selector never assumes them away.
