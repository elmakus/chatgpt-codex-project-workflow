### F1 — epoch reset identity is still syntactic and can bind an unrelated or unaccepted subject

Load-bearing surface: PWV21-REQ-111 and Card acceptance requiring a stable authority/acceptance epoch that ordinary repair cannot reset, with reset allowed only for a **material accepted authority/acceptance redesign** plus durable reset basis.

`tools/state_contract.py::validate_review` accepts an `epoch_reset_subject` when:
- `class = "accepted_redesign"`;
- repository/path are merely non-empty strings;
- commit/blob are merely 40-hex; and
- the path either equals the review acceptance path or starts with `requirements/`, `decisions/`, `planning/` or `workflow/`.

`validate_review_history` then accepts an epoch change when the basis is non-empty and that syntactically shaped subject exists in the attempt. No check binds the reset subject's repository to the selected project/review subject repository, no check binds an authority-root path to one of the workstream's actually accepted authority locators, and no readback proves the claimed commit/blob is the accepted redesign.

Concrete abuse paths therefore still validate:
1. E01→E02 with `repository = "unrelated/repo"`, `path = <exact Task Card acceptance path>`, arbitrary 40-hex commit/blob and any non-empty basis.
2. E01→E02 with a same-project-looking but non-authoritative path such as `requirements/UNACCEPTED_DRAFT.md`, arbitrary 40-hex commit/blob and any non-empty basis.

Both manufacture the label `accepted_redesign` without binding to accepted authority/acceptance, so review counters can still be reset without the material accepted redesign required by authority. The existing reset-abuse fixture rejects a `results/` path but does not falsify foreign-repository or arbitrary authority-root subjects.

Required correction: bind epoch reset to the selected project's exact acceptance subject or one exact workstream-accepted authority locator, with exact immutable readback sufficient to reject foreign-repository, arbitrary-root-path and fabricated-subject resets. Add negative fixtures for those abuse cases while preserving valid accepted redesign reset.

### F2 — global content-set dedup lets real repair rounds evade the per-class ceiling by cycling through earlier failing states

Load-bearing surface: PWV21-REQ-113/PWV21-REQ-137 and Card acceptance requiring a default ceiling of **3 failed repair→closure-verification rounds per material defect class**.

`tools/review_contract.py::review_convergence_state` now stores every RED closure's `repository/path/blob` in a per-class set and derives the round count from `len(set)`. This correctly excludes repeated verification of one unchanged repair and commit-only movement of the same content, but it turns the breaker into a lifetime **unique-content** count rather than a failed **repair-round** count.

Concrete counterexample:
1. RED discovery reviews source S0.
2. Repair produces S1; RED closure R02 → failed round 1.
3. Repair changes S1→S2; RED closure R03 → failed round 2.
4. Repair changes S2→S1; RED closure R04 → this is a third repair→closure round, but S1 is already in the set, so derived count remains 2 and convergence does not trigger.

Alternating S1↔S2 can therefore continue indefinitely without reaching the accepted three-round breaker even though each subject-changing repair followed by RED closure is another failed repair round. No focused fixture covers this cyclic/reverted-content case.

Required correction: derive failed rounds from durable repair transitions/round identity (or equivalent sequencing that counts a content change from the preceding repair state), while still excluding unchanged repeated review, source-discovery reuse and commit-only movement of identical content. Add a positive S1→S2→S1 breaker fixture plus the existing negative cases.
