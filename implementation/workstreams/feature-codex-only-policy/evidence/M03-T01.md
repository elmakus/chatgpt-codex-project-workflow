## Implemented

- Stable Card safety contract now defines explicit opt-in `parallel_safe`, bounded normalized `write_scope` and `exclusive_resources`, with absent metadata remaining serial-valid.
- Planning candidate parallelism is explicitly non-executable; current-state concurrency authority belongs to Execution Prep/JIT.
- Execution Prep deterministically scans READY Cards in canonical Task Board order, greedily builds one pairwise-compatible set, proves one exact recoverable integration base and isolated mutable workspaces, and freezes finite membership/order before launch.
- Selected Task Board M03 state now supports optional `parallel` batch history with stable project-local batch/lane labels, exact integration base, returned result refs, integrated refs and evidence. Concrete runtime identity is excluded.
- Execution keeps Codex Main as the sole shared-state/integration writer. Worker lanes receive one bounded Card/base and return exact result/evidence only.
- Returned lane diffs are checked against frozen base, write scope and reserved shared-state exclusions before Main integrates them in frozen member order.
- Reviewable Card subjects are frozen only after exact Main-integrated Card results are durable. For members of an unresolved current batch, the subject is frozen `pending` but Tester dispatch is deferred until deterministic batch integration closes; post-batch review/finalization/correction drains before unrelated new implementation.
- Recovery covers prepared, in-progress, returned, partially integrated, blocked and complete durable boundaries without replaying completed lane work after runtime loss.
- Post-launch blocked batches now have two explicit recovery shapes: bounded same-member retry under the unchanged frozen contract with failed-result lineage preserved, or terminal launched-batch reconciliation that marks non-integrated member history + Cards blocked before clearing `current_batch`.
- Workstream/Repository contracts apply isolated worktree/equivalent workspace requirements to intra-workstream concurrent local mutation.
- Default and branch-isolated codex_only Task Board templates expose optional batch state while `parallel: null` remains ordinary serial behavior.
- Positive/negative scenario audit covers compatible batches, serial fallbacks, reserved-state/scope escape, integration conflict and crash recovery.

## Independent-review RED-01 repair

The first independent review found that a prepared batch could be cleared after its Cards had already been moved to `in_progress`, with no deterministic reconciliation of those Card statuses.

The corrected contracts now require a pre-launch abandonment transition only while every member remains `prepared` and result-free. Main records the abandoned batch/member outcome as durable `blocked` history with evidence, restores each batch-owned Card to legal READY/serial state, and only then clears `current_batch`. The abandoned batch ID is never reused. Once any member becomes runtime-active or obtains a result, this unwind is forbidden and normal running/returned recovery applies.

The repair also distinguishes the immutable lane `integration_base` from expected Main-owned batch-control bookkeeping commits, so persisting the frozen batch does not invalidate its own implementation base.

## Independent-review RED-02 repair

The second independent review found a reachable ambiguity when a reviewable member was integrated and reviewed before later returned siblings: a RED repair could advance the shared branch and Card result while the active batch still preserved the original member `integrated_commit`, leaving both historical provenance and later sibling integration-head validation underspecified.

The corrected contract now freezes each integrated member's exact M02 subject immediately but defers formal Tester dispatch while that batch remains `current_batch`. Main first transitions the batch to `integrating`, completes all deterministic member integration in frozen order, marks the batch complete and clears `current_batch`. Only then are frozen member reviews dispatched in canonical Task Board order.

If multiple integrated reviewable Cards remain `in_progress` after batch closure, they form one bounded post-batch review drain. That drain permits only review, post-review finalization and bounded RED correction and blocks unrelated new implementation. A later RED repair advances the Card's current result/new review attempt without rewriting the completed batch member's original lane `result_commit`, original `integrated_commit` or original review subject. This preserves exact batch lineage and prevents repair from perturbing the frozen integration chain.

## Independent-review RED-03 repair

The third independent review found that post-launch scope escape, lane failure or integration conflict could mark a current batch/member `blocked` without defining one legal deterministic continuation. The pre-launch unwind was correctly forbidden after runtime-active work, but the contracts did not say how the affected member could be corrected or how a launched blocked batch could safely leave `current_batch`.

The corrected contracts now define exactly two post-launch shapes. A bounded same-member retry is allowed only while accepted authority plus the frozen base/order/write-scope/resource contract remain unchanged; Main preserves the failed result/evidence, clears only the active member result slot, and re-realizes only that member under the same batch/lane/base. If that retry is not legal, Main terminally reconciles the launched batch: runtime-active work is quiesced/reconciled, every non-integrated member history entry and corresponding Card becomes durably `blocked` with exact evidence, integrated/returned refs are preserved, terminal-reconciliation evidence is recorded, and only then may `current_batch` clear. Integrated reviewable members may then form the bounded post-batch review drain even though the closed batch is terminally reconciled `blocked` rather than falsely marked complete.
