## Claim under test

A Card Result can pass the production result parser and become durable no-replay recovery truth even when the result itself says its tests/readback failed, because the parser treats the tests/readback field as an arbitrary non-empty string rather than a semantic success predicate.

The source class also contains malformed implementation-subject and missing-evidence variants. This reproduction deliberately anchors the verdict to the explicit FAILED tests/readback vector so it does not merely duplicate the exact-Git-identity and evidence-existence defects already triaged separately.

## Expected historical acceptance

`workflow/EXECUTION.md` classifies returned implementation before durable reconciliation: only acceptance/evidence-valid implementation is reconciled into an accepted result; incomplete or incorrect implementation remains `in_progress` for correction. The accepted semantic result must record an exact implementation subject, durable evidence, and tests/readback evidence.

A result whose own tests/readback summary is `FAILED: ...` must therefore not be consumed as a valid accepted semantic result or no-replay recovery truth.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `tools/execution_contract.py::parse_card_result()` requires the four result fields to exist and be non-empty, rejects unresolved placeholder brackets, verifies Card ID equality, and validates only the lexical workstream-local shape of evidence refs.
2. It applies no success/failure predicate to `Tests/readback summary`; any non-empty string is returned as `tests_summary`.
3. It applies no exact immutable identity grammar to `Implementation subject`; any non-empty string is returned as `implementation_subject`.
4. In `tools/router.py`, an `in_progress` Card with a result has that artifact parsed by `parse_card_result()`. If its stable Task Card says review requirement `none`, the router immediately returns `route/result_reconciliation` and describes the parsed artifact as a valid semantic result.
5. Source `S024-F05` used the exact result values `Implementation subject: banana`, a nonexistent workstream-local evidence path, and `Tests/readback summary: FAILED: acceptance test failed`; the exact historical parser accepted this input, and the selector reproducer expects `route/result_reconciliation`.
6. `S024` reports that the direct parser counterexample was executed on the exact audited blob. `S016-F05` and `S031-F03` independently demonstrate sibling non-exact-subject acceptance.

The explicit FAILED summary is therefore accepted at the durable result-consumption boundary instead of being classified as unsuccessful implementation.

## Technical verdict

CONFIRMED_MATERIAL

## Why

A durable result is recovery truth specifically because it represents accepted implementation. Treating an explicitly failed tests/readback summary as merely present text lets failed implementation acquire no-replay authority and advance to reconciliation.

This is a semantic acceptance failure even without relying on the separate missing-evidence or immutable-identity defects.

## Smallest relevant implementation boundary

The narrowest boundary for the reproduced defect is `tools/execution_contract.py::parse_card_result()` plus the active-result consume branch in `tools/router.py`.

The parser/consumer must distinguish a successful verified tests/readback outcome from arbitrary non-empty prose before the result can be treated as accepted recovery truth.

## Useful future regression-test shape

1. Valid Card Result with a canonical successful tests/readback representation -> accepted by the result contract.
2. Identical Result except `Tests/readback summary: FAILED: acceptance test failed` -> reject or route correction/recovery; never `result_reconciliation`, review freeze, or finalization.
3. Test explicit negative variants such as failed test count, failed readback, and mixed success/failure text according to the chosen structured contract rather than substring heuristics.
4. Positive route control: an accepted no-review result routes `result_reconciliation`.
5. Negative route control: a semantically failed result remains `in_progress`/correction or fails closed.
6. Separately retain exact implementation-subject and durable-evidence regressions so this semantic-success check does not substitute for those independent guarantees.
