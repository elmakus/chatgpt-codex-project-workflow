## Claim under test

A Plan Review GREEN can be recorded against an authority locator unrelated to the current Definition's accepted requirements/decisions while remaining correctly bound to the frozen plan subject, revision and cycle. That GREEN can then satisfy Planning's review gate.

## Expected canonical semantics

`workflow/PLAN_REVIEW.md` says Plan Review judges one exact immutable frozen Master Plan subject against its accepted Definition/requirements/decisions and planning acceptance surface. Each attempt owns both the immutable plan subject and exact acceptance authority.

`workflow/PLANNING.md` says Strategic Planning converts GREEN Definition authority into executable strategy without silently changing accepted Definition authority. A GREEN independent Plan Review for the exact frozen subject is consumed into approved Planning and causes premium C to become due.

`workflow/DEFINITION.md` makes the current accepted authority concrete: `DEFINITION.toml` binds one approved requirements locator plus accepted decision locators. Therefore the Plan Review acceptance identity is semantically distinct from the reviewed plan subject, but it must still be cross-bound to the current Definition authority against which that plan is judged.

## Minimal reproduction

Construct a valid current Definition and frozen Planning cycle:
- Definition requirements: `requirements/current.md`;
- Definition accepted decision: `decisions/current.md`;
- Planning subject: one exact Git blob at `planning/MASTER_PLAN.md`;
- Planning state: `frozen`;
- premium A satisfied for the current entry subject;
- premium B satisfied for the exact frozen plan subject;
- premium C not due.

Construct one terminal GREEN `PLAN_REVIEW.toml` with:
- exact subject equal to the frozen Planning Git-blob subject;
- matching `plan_revision` and `planning_cycle`;
- semantic independence proof;
- terminal evidence;
- acceptance: `{ class = "authority", path = "workflow/ROUTER.md" }`.

The acceptance path is syntactically legal but is not the current Definition requirements or any accepted current Definition decision.

A portable direct-validator probe is persisted at `audits/pwv21-pre-m03-bug-harvest/repros/H006/repro_plan_review_authority_binding.py`. It validates the frozen Planning record and then calls production `validate_plan_review()` with the unrelated authority locator.

## Observed original-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `validate_definition()` validates the current requirements and decision authority, but its result is not supplied to `validate_plan_review()`.
2. Shared `validate_review()` accepts `acceptance.class == "authority"` by calling `validate_locator(..., "authority", ...)`.
3. The authority locator validator permits any relative path rooted under `requirements/`, `decisions/`, `planning/`, or `workflow/`. It does not know the selected Definition.
4. `validate_plan_review(data, workstream_id, planning)` receives only the review, workstream ID and Planning record. It cross-binds:
   - workstream;
   - plan revision;
   - planning cycle;
   - frozen/approved Planning state;
   - exact review subject to the frozen plan subject.
5. It never compares `data.acceptance` to `definition.requirements` or `definition.decisions`.
6. The production router reads and validates Definition, Planning and Plan Review, but calls `validate_plan_review(..., planning)` with no Definition authority parameter.
7. For frozen Planning with premium B satisfied, a GREEN Plan Review routes to Planning for deterministic approval consumption.
8. After Planning is approved, the same GREEN is accepted as the review gate; premium C can become due and, once satisfied, the router can continue to Execution Prep.

This isolates the two identities requested by the triage: the review SUBJECT is correctly exact and frozen, while the review ACCEPTANCE is unrelated authority.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The canonical Plan Review contract explicitly says the frozen plan is judged against accepted Definition/requirements/decisions. Production validation strongly binds the review subject to Planning but treats acceptance authority as an arbitrary syntactically valid authority locator.

No original-subject cross-record validator makes the state unreachable. Definition authority is validated in its own record, but neither `validate_plan_review()` nor the router establishes that the Plan Review acceptance locator belongs to that current Definition authority set.

The defect is material because GREEN is not inert bookkeeping: the router consumes it into Planning approval, allows premium C progression, and after C is satisfied permits Execution Prep.

This is not the stale-Definition/old-Planning class. The reproduction can keep Definition current and Planning otherwise coherent; only Plan Review's acceptance authority is deliberately unrelated.

## Likely defect boundary

Primary defect boundary: the Stage-6 Plan Review acceptance identity and its cross-record validation against current Definition authority.

A repair should preserve the useful separation:
- SUBJECT = exact frozen plan Git blob;
- ACCEPTANCE = exact accepted Definition/requirements/decisions authority surface.

The missing invariant is not subject equality; it is proving that the acceptance authority is exactly the authority currently owned by Definition (or an explicitly canonical composite derived from it).

No product repair is implemented here.

## Regression shape

A focused regression should keep one exact frozen plan subject constant and vary only Plan Review acceptance:
1. acceptance equal to the canonical current Definition authority surface -> valid.
2. unrelated `workflow/ROUTER.md` -> reject/recover.
3. unrelated requirements file not selected by current Definition -> reject/recover.
4. stale prior Definition requirements/decision path -> reject/recover.
5. exact subject mismatch -> continue to fail independently as today.

A routing regression should prove that a GREEN with invalid acceptance cannot be consumed into approved Planning, premium C, or Execution Prep.
