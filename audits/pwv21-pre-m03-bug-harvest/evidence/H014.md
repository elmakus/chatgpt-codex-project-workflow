## Claim under test

A structurally valid Research record can name an origin owner/subject and a different return owner or Card subject, and the router can trust that independently valid return target instead of failing closed to the exact durable origin.

## Expected canonical semantics

`workflow/RESEARCH.md` assigns Research one exact origin role/subject and one exact return target. Completed Research returns once to its exact durable owner; Research never selects a different target by itself.

For implementation/recovery Research, the selected Task Board owns the obligation and continuation must return to the exact originating Card/owner rather than an unrelated or nonexistent Card.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `validate_research()` validates `origin_role`, non-empty `origin_subject`, and `return_target` independently.
2. Any return target with an allowed execution prefix is accepted; no validator predicate requires the suffix to equal `origin_subject`.
3. The Task-Board Research handler verifies only that `origin_role` is one of `execution_prep`, `execution`, or `execution_resolution`.
4. For completed Research it derives the route from the `return_target` prefix and uses the suffix after `:` directly as the route subject.
5. It does not verify that this suffix equals `origin_subject`, names a Card on the selected Board, or is the applicable originating Card.

Therefore a valid record with `origin_role="execution_resolution"`, `origin_subject="M01-T04"`, and `return_target="execution_resolution:M99"` can validate and route recovery to `M99` rather than fail closed.

The same missing cross-field binding also permits pre-execution owner mismatches such as Intake-origin Research returning to Definition.

## Technical verdict

CONFIRMED_MATERIAL

## Why

Research is non-authoritative factual work with a deterministic return owner. Treating origin and return fields as independently valid strings allows a stale or malformed Research record to redirect workflow ownership.

This is materially load-bearing because the return route can skip the actual durable Card or pre-execution owner, bypassing the exact continuation/recovery obligation that requested the Research.

At frozen candidate `e75a261df0dea3170f3f9c9c0fd535fd055abd6f`:

- no check establishes that the returned Card subject exists on the selected Board or equals the origin subject.

Later PWv2.1 additions around planning seams/live findings do not close this Research origin/return referential-integrity gap.

## Smallest relevant implementation boundary

The smallest defect boundary is the Research origin/return binding consumed by `validate_research()` and the Task-Board Research return handler in `tools/router.py`.

The contract needs an exact cross-field invariant between origin role/subject and return target, plus Board referential validation for implementation/recovery subjects.

## Useful future regression-test shape

1. Board Research: origin `execution_resolution/M01-T04`, return `execution_resolution:M01-T04` and Card exists -> legal return.
2. Same origin, return `execution_resolution:M99-T99` where that Card does not exist -> Recovery.
3. Same origin, return to a different existing Card -> Recovery.
4. `execution:` with empty suffix -> Recovery.
5. Pre-execution Research with `origin_role=intake` and `return_target=definition` -> Recovery.
6. Valid Intake-origin Research returning to Intake -> normal once-only reconciliation.
