## Claim under test

A terminal implementation-review attempt can be rewritten in place at the same path and with the same attempt ID, replacing durable RED history with GREEN semantics without appending a successor attempt.

## Expected canonical semantics

`workflow/REVIEW.md` defines each review attempt as carrying an append-only attempt ID, states that a changed subject or new verdict attempt requires a new attempt, and says existing terminal attempts remain immutable history. Its attempt-history section further says a later attempt never overwrites a prior GREEN/RED file.

Therefore a terminal R01 is a durable historical fact. A later outcome must be represented by a newly appended attempt rather than mutation of R01.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. Task Board `review_attempts` entries use locator class `review_attempt`, whose validator requires only a safe workstream-local `reviews/*.toml` path. Review-attempt locators carry no required immutable commit/blob identity.
2. `validate_review_history()` validates only the currently supplied attempt contents: current attempt IDs, ordering, verdict/evidence shape and Card/workstream binding. It has no prior-version or immutable-attempt-content comparison.
3. The router dereferences each Board attempt locator from the current working tree and parses that current TOML content.
4. With a terminal R01 RED whose subject still matches the current Result, the router reaches `execution_resolution`.
5. If the same R01 file is rewritten in place from `verdict = "red"` to `verdict = "green"` while keeping the path, attempt ID, subject, acceptance and terminal evidence otherwise valid, the current history remains validator-legal.
6. The router now observes GREEN and reaches `post_review_finalization`.

The previously durable RED semantic fact is therefore replaceable without an append-only R02. This matches S028-F05 exactly.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The canonical contract requires immutable terminal attempt history, while production state gives immutable identity to the reviewed result subject but not to the review-attempt artifact itself. Current-state validation cannot distinguish “this is the same terminal R01 as before” from “R01 was rewritten after becoming terminal.”

The defect is material because RED review history is recovery/correction authority and audit truth. Rewriting it to GREEN can erase a failed independent review and change the next workflow obligation to deterministic finalization without preserving the failed attempt.

## Current candidate check

Candidate status: `persists`.

At frozen candidate `e75a261df0dea3170f3f9c9c0fd535fd055abd6f`:
- Task Board review-attempt locators remain path-only; the `review_attempt` locator class still has no commit/blob identity.
- The router still reads each attempt from `attempt_ref["path"]` in the current working tree and passes only the parsed current records to `validate_review_history()`.
- The newer `exact_blob_reader` argument verifies specific immutable subjects used by newer review semantics (for example accepted-redesign epoch reset evidence); it does not bind each review-attempt file to immutable Git content or compare it with a prior terminal version.
- `workflow/REVIEW.md` still requires terminal attempt history not to be overwritten.
- Legacy attempts remain supported. `review_kind()` treats a no-`review_kind` attempt as `discovery`, and `can_finalize_review_obligation()` accepts a GREEN discovery attempt.
- Consequently the exact historical legacy-shaped R01 RED -> same-file R01 GREEN vector remains able to change the current route from RED resolution semantics to GREEN finalization semantics without an appended successor.

PWv2.1 adds convergence, finding and provenance semantics inside the current attempt history, but it does not establish append-only immutable identity for the attempt artifacts themselves.

## Smallest likely defect boundary

The smallest defect boundary is the identity contract between Task Board `review_attempts` and terminal review-attempt artifacts.

A terminal attempt needs durable identity that cannot be satisfied by rewriting the same path, or an equivalent append-only/history readback mechanism that proves previously terminal content is preserved. This audit does not prescribe or implement the repair.

## Useful regression-test shape

Use one REQUIRED-review Card with an exact durable Result:

1. Persist R01 RED, route, and establish RED resolution semantics.
2. Rewrite only that same terminal R01 path/ID to GREEN without appending R02.
3. Assert that the state fails closed or otherwise rejects the mutation; it must not reach post-review finalization.
4. Preserve R01 RED and append a valid R02 GREEN for the same current subject; assert the normal successor-attempt path is accepted when all review rules are met.
5. Repeat with terminal subject, acceptance, independence, and evidence mutations to ensure terminal immutability is not verdict-specific.
6. Include the legacy compatibility shape as a regression case so legacy support cannot be used to rewrite an already terminal historical attempt.
