# H004 Reproduction and Technical Triage

## Exact subjects

- Original audited PWv2 commit: `elmakus/project_workflow_v2@4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`
- Batch current-candidate snapshot: `elmakus/project_workflow_v2@31764d82911de523e36d2de5c5d98ce7c3cedb18`

## Claim under test

A Card whose stable contract requires independent review can be marked `done` and routed to Close without reconstructing the valid result plus the qualifying exact GREEN review proof required to make accepted terminal completion legal.

## Expected canonical semantics

At the original subject, `workflow/STATE.md` says that for REQUIRED/activated RECOMMENDED review, no attempt, pending, in-progress, or RED blocks terminal Card completion, while GREEN for the exact current subject permits deterministic post-review finalization. `workflow/REVIEW.md` states the same blocking lifecycle explicitly.

The result contract is also semantic rather than merely locational: accepted implementation must be reconciled into the exact result with evidence and verified tests/readback. An incomplete or incorrect return remains `in_progress`.

Therefore `done` is not an independent assertion that can manufacture acceptance. It is the terminal state reached only after the result is valid and any required exact review gate has been satisfied.

## Minimal reproduction

Use the production router fixture already exercised by the exact-subject tests.

1. Call the fixture helper equivalent to `install_reviewable_result(project, "required")`. It creates:
   - a stable Task Card whose `Review requirement` is `required`;
   - a structurally exact result locator on the Board;
   - a Result file accepted by the production parser, including GREEN tests/readback and durable evidence.
2. Do not create any review attempt. Keep `review_attempts` empty/absent.
3. Change only the Board Card status from `in_progress` to `done`.
4. Leave the rest of the fixture unchanged.

This deliberately keeps the result valid so the reproduction isolates the required-review proof bypass rather than conflating it with result-validity defects.

### Validator legality

At the original subject, `validate_board()`:
- validates the Task Card locator;
- validates a result locator if present;
- validates review-attempt locators only if any are listed;
- for `status == "done"`, requires only that a result locator exists.

It does not parse the stable Task Card to discover `review_requirement = required`, does not read the Result, and does not require any review attempt or exact GREEN verdict for DONE.

The production test `test_required_review_blocks_until_green_then_routes_finalization` proves the component state is otherwise legal: with the same required-review Card and valid Result still `in_progress`, no review attempt routes to `review_freeze`; pending/in-progress routes to Review; GREEN routes post-review finalization; RED routes correction.

Thus changing only the mutable Board status to `done` does not make an impossible fixture. It removes the Card from the only selector branch that reconstructs the result/review obligations.

## Observed original-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

- `validate_board()` accepts DONE when the exact result locator is present; it has no DONE-to-review coherence check.
- The selector computes `active` only from `status == "in_progress"` and `ready` only from `status == "ready"`.
- Result parsing, Task Card parsing, review requirement discovery, review-history validation, exact-subject comparison, and GREEN/RED routing occur only inside the active-Card branch.
- Once the single Card is `done`, that branch is skipped.
- The all-DONE condition then returns `route / close` owned by `workflow/CLOSE.md`.

The exact-subject tests separately demonstrate both halves of this control flow: required review with no attempt blocks while the Card is active, while an all-DONE Board routes to Close. The missing invariant is the transition/coherence proof connecting those states.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The canonical review contract makes no-attempt/pending/in-progress/RED review incompatible with accepted terminal completion. Yet the Board validator treats `done` as legal with only a result locator, and the router trusts that status before reconstructing the Card's stable review requirement or its exact review history.

No other canonical validator closes the gap. With no attempt there is no review file to validate, and the stable Task Card plus valid Result are individually legal. The production selector itself is the consumer of the cross-record terminal semantics, but it performs those checks only for `in_progress` Cards.

A mutable status flip can therefore erase a real required-review obligation and send the workstream toward Close/finalization.

## Current candidate check

- status: `persists`

The candidate strengthens the prose contract: `workflow/STATE.md` says `done` is reserved for accepted GREEN-reviewed completion, and `workflow/REVIEW.md` says no attempt/pending/in-progress/RED blocks accepted (`done`) terminal Card completion.

However, candidate `validate_board()` still requires only a result locator when status is `done`; review-attempt locators remain optional and are not dereferenced there. The candidate's additional seam/sizing/topology/late-return validation does not reconstruct required review proof for DONE.

For all-DONE state, the new mechanical policy does not cure the gap: `PWV21-K012` is `board_all_cards_done`, consumes only `board.cards`, and routes directly to Close. Therefore the same one-field status transition still bypasses the required GREEN proof at the frozen batch candidate.

## Likely defect boundary

Primary defect boundary: terminal Card state coherence at the Board validation / selector handoff.

The terminal decision needs to reconstruct or cryptographically/durably bind the valid Result and required exact GREEN review proof before `done` may be consumed as accepted completion. The defect is not in Close itself: invalid accepted-terminal state is already trusted before Close receives it.

No repair is implemented here.

## Regression shape

Starting from the production valid fixture:

1. install a valid Result for a Card with `Review requirement: required`;
2. leave review attempts empty;
3. flip only `status = "in_progress"` to `status = "done"`;
4. run the production Board validator and selector.

The regression must reject/recover that state or route back to the missing review obligation; it must never reach Close. Sibling assertions should cover pending and RED exact attempts as non-DONE-compatible states. A positive control with qualifying exact GREEN should still permit deterministic finalization and later Close.
