## Claim under test

A valid durable Card result can be ignored when mutable Card status is nonterminal but not `in_progress`, allowing the same completed work to re-enter launch/correction paths. The minimal reproduced vector is `status = "ready"` plus an otherwise valid durable result.

## Expected historical acceptance

`workflow/STATE.md`, `workflow/EXECUTION.md`, and `workflow/RECOVERY.md` treat a durable valid semantic result as recovery truth and state that runtime/context loss must not replay accepted implementation.

A Card that carries such a result therefore cannot be treated as a fresh READY launch solely because its mutable status bit says `ready`; the state must reconcile from the result or fail closed as contradictory.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `tools/state_contract.py::validate_board()` permits a `result` locator on every Card status. It requires a result when status is `done`, but does not forbid a result on `planned`, `ready`, or `blocked`.
2. `tools/router.py` builds `active` from `status == "in_progress"` and `ready` from `status == "ready"`.
3. The durable-result parse/reconciliation/review path exists only inside `if active:`.
4. The later single-READY branch calls `refresh_ready_card()`, which validates the Card/authority/dependency launch surface but does not consume or reject `card["result"]`, then returns `route/execution_prep`.
5. `S016-F03`, `S008-F03`, and `S028-F04` independently reproduce the READY + valid durable result vector: mutate only the Card status from `in_progress` to `ready` while retaining the result, and the selector routes `execution_prep`.
6. `S023-F04` independently demonstrates a sibling `blocked + result` vector where blocker routing can return `execution` without considering the durable result.

The historical state contract and selector therefore let mutable status override durable completion evidence.

## Technical verdict

CONFIRMED_MATERIAL

## Why

No-replay recovery depends on durable accepted result truth outranking stale or torn runtime status. A READY status that can send a result-bearing Card back toward launch makes an already completed implementation eligible for replay, including potentially repeated external mutations.

The READY vector alone is sufficient to establish the defect; the blocked/planned siblings reinforce that the root is status/result coherence and routing precedence rather than one isolated branch.

## Smallest relevant implementation boundary

The smallest boundary spans Card status/result coherence in `tools/state_contract.py::validate_board()` and result-vs-status precedence in `tools/router.py` / mechanical READY rule `PWV21-K011`.

Either contradictory nonterminal result-bearing states must fail closed, or valid durable result truth must be reconciled before status-specific launch/blocker routing. The invariant cannot depend on `in_progress` being the only status from which results are noticed.

## Useful future regression-test shape

1. Valid complete READY Card with no result -> normal READY launch-refresh / Execution Prep remains legal.
2. Same READY Card with a valid durable no-review result -> must route result reconciliation or fail closed; never Execution Prep.
3. READY + result requiring review -> must enter the appropriate result/review recovery path or fail closed; never launch.
4. `blocked + result` and `planned + result` -> establish the chosen canonical policy explicitly and prove neither can replay implementation while ignoring result truth.
5. Positive control: `in_progress + valid result` continues to route result reconciliation/review rather than Execution.
6. Add torn-state recovery fixtures so persistence interruption between result write and status transition cannot duplicate implementation/external effects.

## Important limitations

The blocked sibling may require a distinct repair interaction with blocker semantics even though it shares the same result-precedence root.

New current-candidate gates such as topology challenges can add an earlier hold for some READY Cards, but they do not make `ready + result` invalid and do not establish result-first recovery; once those independent gates are satisfied, the READY rule still ignores the result.
