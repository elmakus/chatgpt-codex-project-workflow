## Claim under test

Fresh recovery of an `in_progress`, result-less Card can route directly to Execution after proving only that the Card file exists, even when that same file fails the canonical stable Task Card parser.

## Expected historical acceptance

`workflow/EXECUTION_PREP.md` defines the stable Task Card as execution authority: exact Card ID, bounded scope, authority refs, exact dependencies, observable acceptance, tests/readback, review requirement, and optional technical contract. `workflow/EXECUTION.md` says Main performs launch refresh before implementation.

On recovery of an active Card, missing or truncated stable authority therefore cannot be replaced by mere file existence; invalid binding must fail closed rather than authorize implementation.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. The production router fixture's active Card file contains only a heading and one prose sentence: `# Fixture Card` plus `Exact current Card contract used only to prove progressive disclosure.`
2. `tools/state_contract.py::parse_task_card()` requires all stable fields: Card ID, included/excluded scope, authority refs, dependencies, acceptance, required tests/readback, review requirement, and technical contract. The fixture Card therefore fails that parser.
3. In the active-Card branch of `tools/router.py`, the Card contract path is read. `parse_task_card()` is invoked only inside the nested branch where the active Card already has a durable result.
4. When the active Card has no result, control falls through to `route/execution` after the existence/read succeeds; stable Card semantics are never parsed.
5. The repository test `test_active_card_routes_to_runtime_neutral_execution` explicitly expects the malformed default fixture to return `route/execution`.
6. Source reproducer `f4_active_malformed_card_executes` pairs those two operations: the selector routes Execution, then `parse_task_card()` rejects the exact same file.

The historical production route therefore treats file readability as sufficient execution authority for this recovery path.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The stable Task Card is the bounded scope/authority/acceptance contract for implementation. Resuming mutation from an active Card whose durable contract cannot even be parsed means recovery can continue without proving what is authorized, what must be tested, or what review is required.

The fact that the shipped fixture/test expectation encodes this asymmetry makes the defect concrete rather than a hypothetical malformed-state concern.

## Smallest relevant implementation boundary

The smallest boundary is the active/no-result recovery path in `tools/router.py` relative to `tools/state_contract.py::parse_task_card()`.

The selector must establish the stable Task Card contract before an active Card can authorize Execution, not only once a result exists.

## Useful future regression-test shape

1. Active/result-less Card with the current truncated two-line fixture -> Recovery, not Execution.
2. Active/result-less Card missing each stable field in turn (authority, acceptance, tests/readback, review requirement, scope) -> Recovery.
3. Active/result-less Card with a complete valid stable contract and valid required authority inputs -> `route/execution`.
4. Positive recovery control: a complete Card that had already launched remains executable after runtime/context loss without requiring a new launch decision.
5. Result-bearing active Card continues to use the same stable parser before reconciliation/review.
6. Preserve READY launch-refresh tests so validation is consistent across READY -> in_progress -> recovered in_progress transitions.
