## Claim under test

Close can certify source-ref-independent target-side recovery when the caller declares both the required and present recovery-artifact sets empty, after which the cleanup helper can authorize deletion of the exact source ref.

## Expected canonical semantics

Destructive source-ref cleanup is allowed only after target-side durable truth contains the mandatory recovery package needed to reconstruct the accepted workstream independently of that source ref.

The recovery verifier itself therefore must establish the mandatory package boundary. A caller cannot prove completeness merely by under-declaring the required set to empty.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `tools/close_contract.py::verify_target_side_recovery()` verifies non-empty source provenance, immutable merge evidence, and equality of the merged/target package head to the source head.
2. Artifact completeness is then reduced to `required_artifacts - present_artifacts`.
3. Both artifact sets are caller supplied; the helper encodes no mandatory minimum/core recovery classes and does not reject an empty `required_artifacts` set.
4. With matching non-empty heads, `immutable_merge_evidence=True`, and `required_artifacts=frozenset()`, `present_artifacts=frozenset()`, the missing set is empty and the helper returns `source_ref_independent_recovery`.
5. Passing that conclusion as `terminal_package_independent=True` to `cleanup_branch_action()`, with a surviving source ref in `safe_to_delete` state and an exact matching verified head, reaches `delete_exact_ref`.

Thus the recovery-completeness claim can be satisfied without proving that any mandatory recovery artifact exists.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The defect sits directly in the safety gate preceding a destructive cleanup action. The exact-head checks prevent deletion of the wrong ref, but they do not establish that the accepted workstream remains recoverable after the right ref is deleted.

Delegating the definition of the mandatory recovery package entirely to caller-supplied sets allows an empty/under-declared requirement set to convert absence of evidence into a positive recovery certificate.

## Current candidate check

Candidate status: `persists`.

At frozen candidate `003f8a9a7c12a21d0c73b07163e449b8ae63bad8`:

- `verify_target_side_recovery()` retains the same caller-supplied `required_artifacts` and `present_artifacts` interface;
- it still computes only `required_artifacts - present_artifacts`;
- it still has no invariant requiring a non-empty or canonical mandatory recovery package;
- `cleanup_branch_action()` still returns `delete_exact_ref` once the upstream recovery certificate is treated as independent and the exact-head cleanup checks pass.

The empty/empty recovery-certification vector therefore remains present.

## Smallest relevant implementation boundary

The smallest defect boundary is `tools/close_contract.py::verify_target_side_recovery()`: the helper must derive or validate the canonical mandatory target-side recovery package instead of trusting an arbitrary caller-declared required set.

`cleanup_branch_action()` is the downstream destructive consumer and already supplies exact-head/state checks; the material gap is the truth value supplied to its `terminal_package_independent` precondition.

## Useful future regression-test shape

1. Matching heads + immutable merge evidence + empty required/present artifact sets -> reject.
2. Caller supplies an under-declared required set that omits one mandatory recovery class -> reject even when every declared item is present.
3. Canonical complete required package + all required artifacts present -> certify source-ref-independent recovery.
4. Canonical required package with one missing artifact -> reject and never permit deletion.
5. After a valid recovery certificate, stale/mismatched source-ref head must still block deletion.
6. After a valid recovery certificate and exact current head, the normal safe-to-delete path may return `delete_exact_ref`.
