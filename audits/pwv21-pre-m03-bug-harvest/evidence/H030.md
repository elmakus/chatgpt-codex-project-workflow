## Claim under test

Syntactically malformed durable TOML can raise `tomllib.TOMLDecodeError` out of the production selector instead of being converted into the deterministic Recovery obligation required for invalid durable state.

## Historical source evidence

S002-F01 traces the selector's state-read path directly. `tools/state_contract.py::read_toml()` calls `tomllib.load()`; `read_project()` calls `tomllib.loads()`. Python syntax errors from those calls are `tomllib.TOMLDecodeError`.

The source's minimal mutation is to replace a selector-read TOML file, for example `TASK_BOARD.toml`, with invalid syntax such as `revision = [`. The source notes that `tools/state_contract.py`'s own CLI explicitly catches `tomllib.TOMLDecodeError`, while the production selector does not.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

- selector bootstrap catches `(OSError, ValidationError)`;
- the selected-workstream/state envelope catches `(OSError, ValidationError, KeyError)`;
- active/blocked/READY subpaths add domain exceptions but still omit `tomllib.TOMLDecodeError`;
- `read_toml()` does not normalize parser errors into `ValidationError`;
- `read_project()` likewise leaves `tomllib.loads()` syntax errors unnormalized.

Therefore syntactic corruption at a TOML read performed inside those selector regions can bypass `recovery(...)` and surface as an uncaught parser exception.
