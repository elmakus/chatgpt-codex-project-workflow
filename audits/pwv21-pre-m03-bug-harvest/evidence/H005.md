## Claim under test

A prior GREEN implementation review can authorize finalization even when its Task Card acceptance locator is not the Task Board Card's current selected stable contract, so the reviewer may not have evaluated the acceptance surface currently governing the Card.

## Expected canonical semantics

At the original subject, `workflow/REVIEW.md` defines implementation review as an exact-subject blocking gate. Each attempt binds one exact immutable Git content subject and one exact acceptance surface, normally the stable Task Card. Its blocking lifecycle says GREEN for the exact current subject plus acceptance permits deterministic finalization.

`workflow/STATE.md` says stable Task Cards own bounded authority/scope/acceptance/tests/review and that implementation attempts bind one immutable Git subject to its exact acceptance surface. `workflow/EXECUTION_PREP.md` calls the Task Card stable authority and requires launch refresh to reread the selected Task Board and exact Card contract.

Therefore Card identity alone is insufficient: the GREEN must cover the actual selected Task Card acceptance surface, and a changed or different acceptance contract cannot inherit a prior GREEN merely because the Card ID is unchanged.

## Minimal reproduction

Use one `in_progress` Card `M01-T01` with:
- selected Board contract: `implementation/workstreams/ws/cards/M01-T01.md`;
- a valid semantic Result whose immutable subject exactly matches the review subject;
- review requirement `required`;
- one terminal GREEN review attempt for `card_id = "M01-T01"` and `workstream_id = "ws"`;
- review acceptance path: `implementation/workstreams/ws/cards/archive/M01-T01.md`.

The two Task Card paths are deliberately different. The alternate acceptance path still satisfies the production task-card locator rule because it is under the same workstream `cards/` prefix, ends in `.md`, and has basename/stem `M01-T01`. Existence or content identity of that acceptance path is not required by the review validator.

A portable direct-validator probe is persisted at `audits/pwv21-pre-m03-bug-harvest/repros/H005/repro_acceptance_binding.py`. It calls production `validate_review_history()` with that GREEN attempt and demonstrates the acceptance identity can be validator-legal while differing from the selected Card contract path.

## Observed original-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `validate_locator(..., "task_card", ...)` accepts any workstream-local path under `implementation/workstreams/<ws>/cards/` ending in `.md`.
2. `validate_review()` additionally requires only that `PurePosixPath(acceptance.path).stem == card_id`.
3. `validate_review_history()` cross-binds attempts to expected `card_id` and `workstream_id`, but not to the Board Card's selected `contract.path` and not to immutable Task Card content.
4. The production router reads and parses the current selected `card["contract"]["path"]`, then validates review history with only Card/workstream identity.
5. The router separately compares the review's immutable result subject to the current Result subject. If that matches and the verdict is GREEN, it routes `post_review_finalization`.

Thus the Result subject can be exact while the acceptance surface is a different Task Card path. The current contract is parsed to discover that review is required, but the GREEN's acceptance locator is never compared with that contract locator.

The same gap also admits a same-path content-change vector because Task Card acceptance carries no commit/blob identity. The alternate-path vector is the smaller proof because it requires no temporal mutation: both identities can coexist in one static state.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The finding matches the canonical promise exactly. Review acceptance is intended to bind the exact stable Card acceptance surface, yet the production validation boundary reduces Task Card acceptance identity to:
- correct locator class/root;
- same workstream;
- path stem equal to `card_id`.

That is neither exact selected-contract identity nor immutable content identity. The router then consumes GREEN using only exact Result-subject equality and verdict state. No other original-subject invariant cross-binds `attempt.acceptance.path` to `card.contract.path`.

This is material because the acceptance/tests/scope/review contract can differ while the implementation Result remains unchanged, allowing deterministic finalization under acceptance criteria the independent reviewer did not evaluate.

## Current candidate check

Candidate status: `persists`.

At frozen batch candidate `31764d82911de523e36d2de5c5d98ce7c3cedb18`, the same core binding remains:
- task-card locator validation is still prefix/suffix based;
- review acceptance still checks the Task Card path stem against `card_id`;
- the Board still validates its own `card.contract` independently;
- the active-Card router still parses the selected current contract but calls `validate_review_history()` without passing the selected contract path or immutable Task Card identity;
- the router still compares exact review subject only against the current Result subject before allowing GREEN finalization.

PWv2.1 review-history additions introduce accepted-authority paths, epochs, discovery/closure and convergence semantics, but they do not cross-bind the current review acceptance locator to `card.contract.path` or an immutable Task Card blob. The minimal alternate-path case therefore persists.

## Likely defect boundary

The missing invariant is at the cross-record implementation-review acceptance boundary between:
- Task Board `card.contract`;
- the parsed stable Task Card;
- review `acceptance`;
- finalization routing.

A qualifying Card review needs an exact acceptance identity derived from the selected Card contract, with stale/replaced acceptance invalidation. The repair may be path equality plus immutable content identity, or another canonical exact-subject representation, but this harvest does not implement product repair.

## Regression shape

A focused regression should construct one valid current Card and Result, then test:
1. GREEN acceptance at the exact selected immutable Task Card subject -> eligible for normal post-review finalization.
2. Same Card ID, different legal Task Card path -> reject/recover or require a fresh review.
3. Same path with changed Task Card content after GREEN -> prior GREEN becomes stale and cannot finalize.
4. Review acceptance pointing at a nonexistent but syntactically legal Task Card path -> reject/recover.
5. Result-subject exactness remains independently enforced; acceptance binding must not be conflated with Result identity.
