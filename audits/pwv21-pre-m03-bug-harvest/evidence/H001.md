## Claim under test

A Card can carry a valid workstream-local blocker with `class = "human_authority"` while its Task Board status remains `in_progress`; the accepted state then reaches ordinary `execution` without honoring that blocker.

## Expected canonical semantics

At the audited subject, `workflow/STATE.md` says an incomplete/incorrect return remains `in_progress`, but **only a real unresolved blocker moves the Card to `blocked`**. `workflow/EXECUTION.md` makes the same transition explicit: a real unresolved blocker requires persisting proportional blocker state **and marking the Card `blocked`**. `workflow/RECOVERY.md` classifies unresolved human authority/authorization as a **real user stop**, and `workflow/USER_STOP.md` includes unresolved user/product authority and explicit accepted authorization boundaries in the real-stop boundary. `workflow/ROUTER.md` requires contradictory durable binding to fail closed to Recovery.

Therefore a durable `human_authority` blocker cannot coherently coexist with ordinary active implementation and be ignored.

## Observed original-subject behavior

The exact audited `tools/state_contract.py` enforces only `status == "blocked" -> blocker locator required`. If a blocker locator is present on any status, it validates the locator, but there is no inverse invariant requiring a Card carrying a blocker to have status `blocked`. The exact blocker record above satisfies `validate_blocker()`.

The exact audited `tools/router.py` then builds the `active` list from `status == "in_progress"` and processes that branch before it constructs/handles the `blocked` list. With no result on the active Card, it returns ordinary `("route", "execution")`. That active path never reads `card["blocker"]` or the blocker file. Only the later blocked-card path reads the blocker and calls `classify_resolution()`; at this audited subject `human_authority` maps to `("user_stop", True)`.

Independent executable predicate/control-flow probe over the exact audited conditions produced:

```text
board_validator=PASS
blocker_validator=PASS
card_status=in_progress
blocker_class=human_authority
active_count=1
blocked_count=0
production_precedence_outcome=('route', 'execution')
human_authority_resolution_if_reached=('user_stop', True)
```

Thus the blocker state is syntactically/semantically valid under the audited validators, yet the production precedence makes it unreachable as a blocker obligation while the Card remains `in_progress`.

## Why

The accepted durable state contradicts the canonical Card/blocker transition semantics, and the production selector turns that contradiction into ordinary implementation continuation across a documented human-authority stop boundary. This is not merely an intentionally legal intermediate state: canonical docs say a real blocker moves the Card to `blocked`, while contradictory binding must fail closed.
