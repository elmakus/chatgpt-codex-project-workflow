## Claim under test

An active issue Intake can be converted into an `issue_alignment` human stop before diagnosis has produced any concrete repair subject.

## Expected canonical semantics

`workflow/INTAKE.md` defines issue entry as read-only diagnosis first. Only **after a concrete repair outcome is proposed** does the user-alignment/authorization boundary apply.

A pre-repair issue with no concrete `repair_subject` therefore remains owned by Intake diagnosis; the router must not manufacture a stop whose subject is empty.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `validate_intake()` permits an active issue with `repair_subject=""`, `alignment_state="pending"`, empty `alignment_subject`, `response_kind="none"`, and no prior-art binding.
2. The router's diagnosis-prior-art branch is skipped because `repair_subject` is empty.
3. The later active-Intake branch checks only `kind == "issue"` and `alignment_state == "pending"`.
4. With `response_kind == "none"`, it returns `stop / issue_alignment` and uses the empty `repair_subject` as the stop subject.
5. The emitted reason itself says a repair has been proposed even though the durable record has no repair subject.

Thus legal pre-repair diagnosis is stopped as if a repair proposal already existed.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The stop crosses a human-authority boundary that the Intake contract introduces only after diagnosis has produced a concrete repair proposal. An empty repair subject means there is nothing yet for the user to align with or authorize.

This is not merely an imprecise message: the route changes ownership from continued Intake diagnosis to a real user stop and can halt a legal deterministic continuation.

## Smallest relevant implementation boundary

The smallest defect boundary is the active issue-alignment routing predicate in `tools/router.py`, together with the Intake state invariant that distinguishes pre-repair diagnosis from post-diagnosis alignment.

A human alignment stop must require a concrete current repair subject; otherwise active Intake remains the owner.

## Useful future regression-test shape

1. Active issue, `repair_subject=""`, pending alignment, no response -> route Intake diagnosis, not stop.
2. Same pre-repair state with question/concern metadata but still no concrete repair subject -> do not route Brainstorming as repair alignment.
3. Active issue with concrete repair subject but missing required diagnosis prior-art -> route Intake/Research obligation before alignment.
4. Concrete repair subject + exact prior-art satisfied + no subsequent response -> real `issue_alignment` stop.
5. Concrete repair subject + exact prior-art + question/concern/alternative -> Brainstorming.
6. Authorized response must remain bound to the exact non-empty repair subject.
