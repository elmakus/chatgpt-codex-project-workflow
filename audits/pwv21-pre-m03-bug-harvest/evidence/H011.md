## Claim under test

An unactivated RECOMMENDED implementation review cannot be represented because the stable Task Card schema carries only `none|required|recommended`, while routing treats `recommended` as blocking.

## Expected canonical semantics

PWV2-REQ-036 and `workflow/REVIEW.md` require REQUIRED review and **activated RECOMMENDED** review to block completion until GREEN. The activation is described as occurring through the stable Card/workstream contract.

The relevant question is therefore not merely whether `recommended` blocks, but whether a Task Card that durably declares `Review requirement: recommended` is still an unactivated recommendation.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `parse_task_card()` accepts the stable field `Review requirement` with values `none|required|recommended`.
2. A result-bearing Card with `review_requirement == "none"` may proceed to result reconciliation without independent review.
3. Any other declared review requirement with no attempt routes to `review_freeze`.
4. Therefore the S025-F04 fixture with `Review requirement: recommended` and no attempt does route to `review_freeze`.

That routing behavior is real, but the source reproducer does not establish the premise that this durable Card declaration is **unactivated**. The canonical text says RECOMMENDED becomes blocking when activated by the stable Card/workstream contract, and the reproduced state is itself a stable Task Card contract explicitly declaring `recommended`.

No canonical requirement inspected at the exact subject requires a second activation bit, activation record, or separate state after the stable Task Card has declared the recommendation.

## Technical verdict

REJECTED

## Why

The reported behavior does not demonstrate a contradiction with the assigned canonical semantics. It demonstrates that a stable Card whose review requirement is explicitly `recommended` is treated as carrying a blocking review obligation.

The phrase “activated by the stable Card/workstream contract” is consistent with the stable Card declaration itself being the activation mechanism. Under that reading, an unactivated recommendation is not represented as `Review requirement: recommended` on the Card at all; it has not yet become a Card review requirement.

The source finding would require additional authority establishing that `recommended` means “recommended but not activated” or that activation is a distinct durable dimension. No such requirement was found in the assigned historical authority. Adding a second activation field would therefore be a policy/schema change rather than a demonstrated correctness repair.

## Smallest likely defect boundary

No product defect boundary is established for H011.

If future authority intentionally introduces a durable distinction between an unactivated recommendation and an activated recommendation, the smallest implementation boundary would be the stable Task Card review-requirement contract plus the router predicate consuming it. That would be new/clarified policy authority, not a repair justified by this finding alone.

## Useful regression-test shape

Preserve the existing blocking behavior for a stable Card that explicitly declares `Review requirement: recommended` unless authority is changed.

If a future specification defines a separate activation state, add paired fixtures that prove:

1. recommended + explicitly unactivated -> does not block;
2. recommended + explicitly activated -> blocks exactly like REQUIRED;
3. required -> blocks regardless of recommendation activation machinery;
4. none -> does not acquire a review obligation.

Such a test must bind its expected behavior to the new explicit authority rather than infer an activation bit that is absent from the current contract.

## Limitations

The canonical wording does not contain a sentence literally defining “the `recommended` Task Card value is the activation event.” The rejection rests on the stronger point that the source repro does not prove the opposite, while the requirement explicitly locates activation in the stable Card/workstream contract and specifies no second durable activation state.

The triage dispute is semantic authority, not whether `recommended` routes to review.
