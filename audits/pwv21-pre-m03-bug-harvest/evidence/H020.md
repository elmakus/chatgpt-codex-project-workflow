## Claim under test

The READY dependency launch-refresh path can consume bytes that differ from the immutable Git subject declared by the DONE predecessor and the dependent Card, because the production check proves only metadata equality and path readability rather than the actual Git object identity of the consumed result.

## Expected historical acceptance

`workflow/STATE.md` and `workflow/EXECUTION_PREP.md` require predecessor dependencies to be refreshed against the exact durable result identity and to fail closed when the dependency is stale or has changed.

The historical aggregate identifies this as a load-bearing exact-subject invariant used to prevent changed predecessor results from crossing the launch boundary.

## Observed historical-subject behavior

At `4fb4bfb7d7b1481d6f347c182fc96a5a1135e045`:

1. `tools/router.py::refresh_ready_card()` builds `done_results` solely from the Board-declared `result.path`, `result.commit`, and `result.blob` fields of DONE Cards.
2. For each dependency parsed from the READY Card contract, it checks only that the same declared tuple is present in `done_results`.
3. After the tuple comparison, it reads `dependency["path"]` from the current project filesystem, but it never resolves `dependency["commit"]` or `dependency["blob"]` through Git and never hashes the current bytes to prove that the file read is the declared blob.
4. Therefore a DONE predecessor and READY successor can both continue to declare the same stale tuple while the bytes at the dependency path change; the tuple membership test still succeeds and launch refresh continues.
5. The repository test `test_ready_card_stale_dependency_fails_closed_before_launch` does not cover that case. It changes the Board's commit/blob declarations together with the file contents, so the router rejects the metadata mismatch before any real object-identity proof would be needed.

This confirms the S001-F01 same-path mutation vector: the consumed dependency bytes can differ from the declared immutable Git subject while the production launch gate remains satisfied.

## Technical verdict

CONFIRMED_MATERIAL

## Why

The exact Git subject is the stale-input and recovery-truth boundary for dependency launch. Comparing two copies of the same declaration proves internal consistency only; it does not prove that the file subsequently consumed is the named Git object.

A same-path content mutation with unchanged metadata therefore bypasses the immutable-identity guarantee and can launch downstream execution from a predecessor result the stable Card contract did not actually bind.

## Smallest relevant implementation boundary

The smallest defect boundary is `tools/router.py::refresh_ready_card()` at the READY dependency refresh seam, together with whatever Git-object readback helper is intended to prove a result locator's repository/commit/path/blob identity.

The fix boundary does not require changing all workflow state semantics at once: one regression can require the launch gate to resolve the declared immutable dependency subject and compare the consumed bytes/object identity before accepting the dependency.

## Useful future regression-test shape

1. Create a DONE predecessor result and READY successor whose dependency tuple exactly matches the Board.
2. Establish the tuple against the original result bytes.
3. Mutate only the result bytes at the same path while leaving Card and Board `commit/blob` fields unchanged.
4. READY refresh must fail closed before returning Execution Prep.
5. Control case: unchanged bytes with a resolvable matching Git subject -> launch refresh succeeds.
6. Negative identity cases should additionally cover nonexistent commit/blob and a blob that exists but does not correspond to the declared path at the declared commit.
